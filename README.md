# Контракт API библиотеки

Основной результат — `openapi.yaml`, контракт OpenAPI 3.1 сервиса «Библиотека».
Он описывает Books, Readers и Loans: допустимые запросы, поля ответов, HTTP-статусы,
ошибки и бизнес-правила. Контракт является спецификацией будущего сервера.

Репозиторий: https://github.com/Sofa9890/library-api

- `openapi.yaml` — основной файл для проверки преподавателем.
- `STYLE.md` — 10 правил API.
- `REVIEW.md` — саморевью и границы проверки.
- `GUIDE.md` — пошаговый разбор и текст защиты.
- `verify_contract.py` — проверка структуры и примеров.
- `mock_server.py` — демонстрация фиксированных GET-ответов из контракта.
- `.run/` — готовые конфигурации PyCharm.

## Установка

Python 3.12.x. В корневой папке проекта на macOS/Linux:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

Windows PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

Если `.venv` уже создано, достаточно активировать его. Версии зависимостей
закреплены в requirements.txt; окружение, кеши и `.idea` не включаются в Git.

## Проверка

```bash
python verify_contract.py
python -m openapi_spec_validator openapi.yaml
ruff check .
ruff format --check .
```

Ожидаются OpenAPI 3.1: valid, 16 операций, 25 именованных примеров,
77 проверенных примеров запросов/ответов и 7 отклонённых некорректных запросов.
Динамические бизнес-правила описаны текстом: эти проверки не исполняют
транзакции настоящего сервера.

## PyCharm

Откройте File → Open → папку `library-api`. Выберите Python 3.12 из локального
`.venv/bin/python` (Windows: `.venv\Scripts\python.exe`).

В верхнем списке Run доступны две конфигурации:

- `Validate_library_api` — проверка контракта, завершается с exit code 0;
- `Mock_library_api` — GET-mock на http://127.0.0.1:8013, работает до Stop.

Для чтения контракта откройте openapi.yaml. Это YAML-данные, их не запускают
как Python-файл; запускается программа проверки или mock.

## Mock и curl

В одном терминале:

```bash
python mock_server.py
```

В другом терминале:

```bash
curl -i http://127.0.0.1:8013/v1/books
curl -i http://127.0.0.1:8013/v1/books/1
curl -i 'http://127.0.0.1:8013/v1/loans?status=overdue'
curl -i http://127.0.0.1:8013/v1/books/999
```

Первый запрос вернёт 200 и BookList, второй — Book, третий — пример просроченной
выдачи, четвёртый — 404 и ErrorResponse. Ответы помечены
`X-Mock-Server: fixed-examples-only`.

Mock обслуживает фиксированные примеры GET книг, читателей и выдач из
components/examples. Это демонстрация формы данных, а не реализация библиотеки:
он не хранит изменения, не выполняет CRUD, транзакции, динамические правила
или replay. Кроме `status=overdue` у /loans, фильтры/сортировка/пагинация
в mock не исполняются; такой запрос явно возвращает 501. В полном контракте
все эти возможности описаны. Даты примеров фиксированы, смысл overdue показан
относительно даты примера 2026-10-30.

Файл контракта доступен и по http://127.0.0.1:8013/openapi.yaml.
Остановить mock: Ctrl+C в терминале или красный Stop в PyCharm.

## Важные решения контракта

Базовый путь /v1/ указан в servers; URL сервера записан без конечного слеша,
чтобы пути /books и /loans образовывали /v1/books и /v1/loans.
Поля запросов и ответов разделены. available_copies вычисляет сервер из общего
количества и числа активных выдач; клиент не может прислать это поле.

Все описанные коллекции имеют фильтры, сортировку и limit/offset. Даты сравниваются
по календарю UTC. Просроченной считается активная выдача с due_date раньше
текущей даты. Новая выдача требует due_date строго позже текущей даты.

Idempotency-Key обязателен при POST /loans. Ответ хранится 24 часа после завершения.
Повтор с тем же телом возвращает исходный статус, тело и прикладные заголовки.
Другой запрос с этим ключом даёт 409 IDEMPOTENCY_MISMATCH. Конкурентный запрос
того же тела получает 409 CONFLICT и Retry-After: 1. Запись выдачи и replay-ответа
фиксируются атомарно. Политика подробно описана в операции и x-idempotency-policy.

## Изменения при переходе к v2

Совместимость оценивается с точки зрения уже существующего клиента v1.

| Изменение | Совместимость | Причина |
| --- | --- | --- |
| Новая независимая операция /v2/reports | Совместимо с существующими клиентами v1 | Старые пути и поведение v1 остаются доступны. |
| Новое необязательное поле запроса с прежним поведением по умолчанию | Совместимо | Старый клиент продолжает отправлять старый набор полей. |
| Расширение допустимой длины title в запросе | Совместимо | Ранее допустимые запросы остаются допустимыми. |
| Новое поле ответа Book без изменения схемы v1 | Несовместимо при строгой проверке ответа | В текущей схеме additionalProperties=false; старый валидатор отвергнет поле. |
| Переименование full_name в name | Несовместимо | Меняется имя поля, ожидаемое клиентом. |
| Новое обязательное поле запроса | Несовместимо | Старый запрос перестаёт проходить проверку. |
| Изменение id с integer на string | Несовместимо | Меняется тип и код клиента для работы с ним. |
| Замена limit/offset на cursor без сохранения старого режима | Несовместимо | Старые query-параметры и форма пагинации больше не работают. |
| Смена 201 на 200 при replay POST /loans | Несовместимо | Нарушается обещанный полный replay. |
| Новое значение enum code | Потенциально несовместимо | Старый клиент может проверять закрытый enum или иметь исчерпывающую обработку. |
| Снижение лимита активных выдач с 5 до 3 | Несовместимое изменение поведения | Ранее разрешённый запрос может быть отклонён. |

Несовместимые изменения выносятся в /v2; /v1 сохраняется на объявленный период
миграции. Поле deprecated само по себе не удаляет поле и не делает удаление совместимым.
