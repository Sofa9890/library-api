# Третья лабораторная с нуля

Мы проектируем API библиотеки. Результат — договор между клиентом и сервером:
куда отправить запрос, какие данные передать, что получить и какие ошибки возможны.
Этот договор записан в openapi.yaml. Проверка YAML не заменяет реализацию сервера.

## Что открыть и запустить

1. В PyCharm выбери File → Open → папку library-api.
2. Выбери интерпретатор Python 3.12 из .venv этого проекта. На подготовленном
   компьютере окружение уже создано. Для нового компьютера команды есть в README.
3. Открой openapi.yaml — это основной файл лабораторной.
4. В верхнем списке Run выбери Validate_library_api и нажми зелёный треугольник.
   Сообщение OpenAPI 3.1: valid и exit code 0 означают успешную проверку.
5. Для демонстрации выбери Mock_library_api и нажми Run. Открой в браузере
   http://127.0.0.1:8013/v1/books или выполни curl из README.
6. Mock работает, пока не нажмёшь Stop. Он показывает фиксированные GET-ответы.

В терминале те же действия:

```bash
source .venv/bin/activate
python verify_contract.py
python mock_server.py
```

## Что означает API

Представь читательское приложение и сервер библиотеки. Приложению нужно узнать,
какие книги есть. Оно отправляет GET /v1/books. Сервер отвечает JSON со списком.
Обе стороны должны заранее договориться о URL, полях и возможных результатах.
OpenAPI формализует этот договор, чтобы его могли читать и люди, и инструменты.

YAML — формат записи структурированных данных с отступами. OpenAPI — стандарт,
который определяет, какие разделы и значения должны быть в этом YAML.
JSON — формат тела HTTP-запросов и ответов в нашем API.

## Три ресурса

Book — карточка книги: номер, название, автор, ISBN, год и количество экземпляров.
Одна карточка может описывать пять одинаковых физических экземпляров.

Reader — читатель: номер, имя, email и дата регистрации.

Loan — конкретная выдача: какая книга, какому читателю, когда выдана,
когда должна быть возвращена и когда фактически возвращена.
book_id и reader_id связывают выдачу с книгой и читателем.

Если returned_at равно null, книгу ещё не вернули. Если записана дата и время,
выдача завершена. Просроченная выдача всё ещё активна и занимает экземпляр.

## Как читать openapi.yaml

- openapi: 3.1.0 — версия стандарта.
- info — название и версия нашего API, это отдельная версия от стандарта OpenAPI.
- servers — базовый адрес с /v1. Путь /books дополняет его до /v1/books.
- tags — группы Books, Readers и Loans для документации.
- paths — список адресов и разрешённых операций.
- parameters — аргументы в URL или заголовках.
- requestBody — тело, которое отправляет клиент.
- responses — возможные статусы и тела ответа сервера.
- components/schemas — переиспользуемые описания формата данных.
- components/examples — конкретные примеры.
- $ref — ссылка на описание внутри того же документа, а не копия другого проекта.

Например, `$ref: '#/components/schemas/Book'` означает «используй схему Book».
required перечисляет обязательные поля, type задаёт тип, minimum — нижнюю границу,
additionalProperties: false запрещает поля, которых нет в схеме.

## Разница между методами

GET /books — получить список. POST /books — создать карточку книги.
GET /books/1 — прочитать одну книгу. PUT /books/1 — заменить все редактируемые
поля. PATCH /books/1 — передать только изменяемые поля. DELETE /books/1 — удалить.

CRUD — Create, Read, Update, Delete: создание, чтение, изменение, удаление.
Books и Readers имеют полный CRUD.

Выдачи сохраняют историю, поэтому возврат — POST /loans/501/return.
Удаление выдачи уничтожило бы сведения о том, кто и когда брал книгу.
Повтор возврата возвращает прежний результат и не добавляет лишний экземпляр.

## Что отправляет клиент и что вычисляет сервер

Для создания книги клиент передаёт title, author, isbn, published_year и total_copies.
Сервер сам присваивает id и вычисляет available_copies.

Пример: всего 5 экземпляров, 2 ещё не вернули. Доступно 5 − 2 = 3.
Клиент не может прислать available_copies: 100 и искусственно увеличить остаток.
Для этого серверное поле отсутствует в схемах запросов и помечено readOnly в ответе.

Для выдачи клиент передаёт book_id, reader_id и due_date. Сервер задаёт id,
loaned_at и returned_at. В новой выдаче returned_at будет null.

## Проверка формы и проверка смысла

Схема может проверить, что book_id — положительное целое число, due_date — дата,
а неизвестных полей нет. Это проверка формы данных.

Наличие свободного экземпляра, существование читателя, число его активных выдач
и сравнение due_date с сегодняшней датой зависят от состояния сервера.
Эти проверки описаны контрактом, но исполняться будут в серверной программе.

Выдать книгу можно, когда доступен хотя бы один экземпляр и активных выдач
у читателя меньше 5. Новая due_date должна быть позже сегодняшней даты UTC.
Удаление книги или читателя с активной выдачей запрещено.

## Фильтры сортировка и страницы

```text
GET /v1/books?author=Мартин&sort=title,-id&limit=20&offset=0
GET /v1/loans?status=overdue
```

author отбирает книги автора. sort задаёт порядок; минус означает убывание.
limit задаёт размер страницы, offset — сколько записей пропустить.
total в ответе показывает, сколько записей подходит под фильтры до разбиения
на страницы. Пустой список — нормальный результат 200, а не ошибка 404.

Эти примеры описывают полный будущий API. Учебный mock поддерживает только
фиксированные GET-примеры и вариант overdue, остальные возможности — в контракте.

## Идемпотентность на понятном примере

Ты нажала «выдать книгу», запрос дошёл до сервера, но ответ потерялся.
Клиент повторяет запрос. Нам нужна одна выдача, а не две.

Поэтому POST /loans требует заголовок Idempotency-Key. Он идентифицирует
попытку одной конкретной операции. Для повтора этой операции ключ сохраняется.
Для другой выдачи нужен новый ключ.

- Тот же ключ и те же данные после завершения → тот же статус, тело и прикладные заголовки.
- Тот же ключ и другие данные → 409 IDEMPOTENCY_MISMATCH.
- Первый запрос ещё обрабатывается → 409 CONFLICT и Retry-After: 1; повторить позже.
- Через 24 часа после завершения запись истекает, ключ снова считается новым.

Важно сохранить ответ вместе с выдачей. Иначе сервер может создать выдачу,
упасть до сохранения ключа и затем создать дубликат при повторе.
Это называется атомарностью: связанные изменения фиксируются как единое действие.

## Статусы и ошибки

200 — успешно прочитали или изменили. 201 — создали новый ресурс;
Location указывает, где его прочитать. 204 — удалили, тела нет.
400 — запрос нельзя правильно разобрать. 404 — конкретный ресурс не найден.
409 — состояние конфликтует с запросом. 422 — поля или дата нарушают ограничения.

ErrorResponse объединяет ошибки в один формат. HTTP-статус — общая категория,
code — конкретная машинная причина, message — объяснение человеку,
details — сведения о проблемных полях, request_id — идентификатор для поиска в логах.

## Что проверяют программы помощники

verify_contract.py читает YAML и запускает валидатор OpenAPI. Затем проверяет
форму примеров, запрещённые поля, набор операций и наличие политики идемпотентности.
Он не выполняет реальную выдачу и не проверяет работу базы данных.

mock_server.py читает examples из этого же YAML и возвращает их по GET.
Заголовок X-Mock-Server сообщает, что это демонстрация. Полноценная реализация
CRUD, транзакций и защиты от повторов в mock не входит.

## Текст защиты

«Я спроектировала OpenAPI 3.1 контракт сервиса библиотеки. Есть три ресурса:
книги, читатели и выдачи. Для книг и читателей описан полный CRUD; для выдач —
создание, список, получение по номеру и возврат отдельным POST-запросом.
Запросы и ответы имеют отдельные схемы, серверные поля клиент не передаёт.
Коллекции поддерживают фильтры, сортировку и пагинацию. Ошибки приведены
к единому ErrorResponse. Для создания выдачи описан Idempotency-Key:
повтор исходного ответа, конфликт другого тела, параллельные запросы и срок
хранения 24 часа. Бизнес-правила учитывают остаток, лимит пяти выдач и даты.
Контракт проверен валидатором и проверками примеров. Для демонстрации я добавила
mock GET-ответов с curl, а также таблицу совместимости изменений v2».

Главное для понимания: объясни на своём примере, чем создание выдачи отличается
от чтения книги и почему повтор запроса не должен выдавать ещё один экземпляр.
